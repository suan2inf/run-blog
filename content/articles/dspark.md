# DSpark 读后感

## 核心思想

传统投机解码的核心思想是使用 draft 模型先自回归生成一定量的 token 作为草稿，然后由 target 模型做前向传播验证比对接受，一旦不接受，后面舍弃。所以说每个 token 的生成时延就等于 $(T_{\text{draft}} + T_{\text{verify}})/\tau$。要降低时延，就有三个关键点：降低草稿生成时间、降低验证时间、增加接受 token 数量。过去的解决方案，如 DFlash 采用了并行草稿生成器来降低草稿生产时间，但这样的话由于并行不依赖于前缀，导致后缀的接受率会出现灾难性的崩塌。所以 DSpark 的核心设计，就是同时加速优化这三者：采用半自回归生成器，让模型起草更快、可接受度更高；采用置信度调度验证，注入置信度，这样 target 模型就可以并行验证置信度，来减少验证时间。

## 具体技术细节

### 半自回归生成

半自回归生成的核心，是先用并行前向传播把整个 draft 块的 logits 一次性算出来，再从左往右逐个采样，并在采样时注入顺序偏置。

这里要区分清楚两步：并行阶段产出的是各个位置的 logits（也就是每个位置一整套概率分布），并没有真正定下 token；真正的 token 是在顺序阶段从左往右采出来的。因为并行阶段每个位置是对所有可能前驱做边际化，而不是以实际采到的那个前驱为条件，块内越靠后越容易采出互相矛盾的组合，接受率会快速衰减。顺序偏置补的正是这个缺失的条件依赖：每采一个 token，就把前文采出的 token 所造成的偏置加进当前分布，让后面的 token 真的知道前面采了什么。

因为加了顺序依赖，采样必须串行（第 $k$ 个位置要用到 $x_{<k}$），所以负责注入偏置的那一层必须极轻量，让整体草稿时延仍由并行阶段主导——这就是"半"自回归的由来：$T_{\text{sequential}} \ll T_{\text{parallel}}$。

**Markov 头**

马尔可夫头是最简单的实现方式：只让偏置依赖前一个 token。

$$B(x_{k-1},\cdot) = W_1[x_{k-1}]\,W_2 \in \mathbb{R}^{\mathcal{V}}$$

原则上这是一个完整的 $\mathcal{V}\times\mathcal{V}$ 转移矩阵：行是前一个 token（$\mathcal{V}$ 种可能），列是正在预测的 token，第 $x_{k-1}$ 行就是"上一个 token 是 $x_{k-1}$ 时，给所有候选 token 各加多少偏置"。但 $\mathcal{V}\approx 10^5$ 时 $\mathcal{V}^2$ 有 $10^{10}$ 个数，存不下也算不动，所以做低秩分解 $B = W_1W_2$：$W_1$ 是 $\mathcal{V}\times r$，每个 token 对应一行 $r$ 维的"身份码"；$W_2$ 是 $r\times\mathcal{V}$，把身份码投影成 $\mathcal{V}$ 维偏置。$r$ 默认 256，参数量从 $10^{10}$ 降到约 $5\times 10^7$。用的时候就是查表（取 $W_1$ 的第 $x_{k-1}$ 行）再投影，所以每步只是一次查表加一个 $256\times 10^5$ 的矩阵乘，非常轻量。

代价是：$W_1W_2$ 的秩最多是 256，所有行的偏置被压进同一个 256 维子空间，不可能各行独立。这里赌的是 token 之间的转移偏好本身存在大量冗余、可用低维表达，属于经验上的近似，不是无损。

**RNN 头**

RNN 头让状态累积整块历史，不受"只看前一个"的限制，但要维护循环状态、实现更复杂、部署性质也更差，而原作实测它相对 Markov 头只有很小的额外收益，所以默认不用它。

### 置信度调度验证

**朴素理解**

置信度头负责"给数"：对草稿块里的每一个位置，估计这个 token 能活过验证的概率。

硬件感知前缀调度器负责"用数"：拿这些概率，结合当前硬件负载，决定这一步实际验证多少个 token。

这一层理解我确认过：置信度头不参与决策，调度器不做预测，**头给数、调度器用数**，耦合点就在这。

按我目前的理解，调度器其实不只是"决定验证多长"，它本质上是在做**资源调度**——它按存活概率从高到低排序候选 token，然后在容量预算内取一个 top-K。这个容量预算就是 batch 容量，而 batch 容量和引擎每秒能跑多少步的关系（论文里那条 SPS 曲线）是提前 profile 出来的。

**数学推导**

**一、涉及的四个量**

$$a_{r,j}=\prod_{i\le j}c_{r,i}$$

前缀存活概率，逐位置累乘。

$$B=\sum_{r=1}^{R}(1+\ell_r)$$

这一步送进目标模型的 token 数。

$$\tau=\sum_{r=1}^{R}\Big(1+\sum_{j=1}^{\ell_r}a_{r,j}\Big)$$

这一步期望能收下的 token 数。

$$\Theta=\tau\cdot\mathrm{SPS}(B)$$

系统每秒产出的 token 数，也就是要最大化的目标。

其中 $R$ 是活跃请求数，$\ell_r$ 是调度器给请求 $r$ 定的验证长度（取值 $0$ 到 $\gamma$），$c_{r,i}$ 是置信度头输出的第 $i$ 个位置的条件存活概率，$\mathrm{SPS}(B)$ 是"batch 有 $B$ 个 token 时引擎每秒能跑几步"——它在引擎初始化时离线 profile 一次，存成一张小表。

**二、$\tau$ 为什么长这样**

$\tau$ 由两部分组成。

第一部分是**保底收获**。哪怕一个草稿都不验（$\ell_r=0$），目标模型跑一次前向也会从自己的分布里采一个 token 输出，这一个必定到手。$R$ 个请求就是 $R$ 个，这就是式子里那个 $\sum_r 1$。

第二部分是**草稿的期望收获**。第 $j$ 个草稿位置能不能被收下，要求"前面 $1$ 到 $j-1$ 位全部被接受，且第 $j$ 位自己也被接受"——因为投机解码只接受连续前缀。而这件事的概率恰好就是 $a_{r,j}$，因为 $c_{r,i}$ 的定义就是"前面都活着的前提下，第 $i$ 位能活"这个条件概率。所以直接用期望的线性性，把 $\ell_r$ 个概率加起来就行，**不需要各位置相互独立**。

（也可以用另一种方式验证：记"恰好收下 $k$ 个草稿"的概率是 $a_k(1-c_{k+1})$，对 $k$ 求期望再做一遍分部求和，会塌成 $\sum_j a_j$，结果一致。）

**三、$\Theta$ 为什么是乘**

$$\underbrace{\tau}_{\text{每步收几个 token}}\times\underbrace{\mathrm{SPS}(B)}_{\text{每秒跑几步}}=\underbrace{\Theta}_{\text{每秒产几个 token}}$$

量纲上是自洽的。这就是系统总吞吐——GPU 每秒能给所有用户吐出多少 token。

调度器的任务因此清楚：$\ell_1,\dots,\ell_R$ 是要选的量。多验一点，$\tau$ 涨，但 $B$ 涨、$\mathrm{SPS}$ 跌。**要在"多赚的 token"和"每秒少跑的步"之间找平衡。**

**四、为什么可以贪心**

贪心成立的根据只有一条：**把请求 $r$ 的验证长度从 $j-1$ 延到 $j$，期望接受 token 的增量恰好是 $a_{r,j}$。**

因为 $\tau$ 里位置 $j$ 的贡献就是 $a_{r,j}$，加上去就多这么多，没有别的耦合项。

而 $a_{r,j}$ 对 $j$ **单调不增**（累乘只会越乘越小）。这一条带来两个后果：

1. **块内前缀依赖自动被满足**。你不可能"跳过位置 2 只验位置 3"。而把所有请求的所有候选位置按 $a_{r,j}$ 全局排序后，同一请求的位置天然按 $j=1,2,3\dots$ 的顺序出现，所以取排序列表的前缀永远不会出现非法跳跃。
2. **每个候选的成本都一样**（都是往 batch 里加 1），所以只比收益就够了。如果总预算 $B$ 固定，最优解就是取收益最大的那 $B$ 个——也就是排序列表的前缀。

算法因此长这样：初始让所有 $\ell_r=0$（$B=R$，$\tau=R$），然后沿排序列表依次录取，每录取一个就更新 $B$ 和 $\tau$、重算 $\Theta$，**一旦 $\Theta$ 下降就停**。

**五、单峰性——早停为什么有效，以及它的条件**

早停能工作，靠的是 $\Theta$ 沿这条路径**先升后降**（单峰）。论文的措辞是 if and only if：逐步早停能取到全局最优吞吐，**当且仅当** $\Theta$ 是单峰的。

那单峰又靠什么？靠**收益的衰减速度压过 SPS 的波动幅度**。

记第 $k$ 步的边际收益是 $g_k$（就是那一格候选的 $a$ 值），SPS 从 $B$ 到 $B+1$ 的比值是 $\rho_k=\mathrm{SPS}(B+1)/\mathrm{SPS}(B)$。要让 $\Theta$ 的增量一路递减，核心要求是 $g_k$ 掉得够快、或者 $\rho_k$ 波动够小。光滑曲线之所以安全，是因为它的 $\rho_k$ 每步都接近 1，被 $g_k$ 的衰减稳稳压住。

**所以"光滑"是充分条件，不是根本条件。** 根本条件是上面那条衰减关系。

**六、数值例子**

三个请求，$\gamma$ 分别是 3、2、1：

| 请求 | $c_{r,1},c_{r,2},c_{r,3}$ | $a_{r,1},a_{r,2},a_{r,3}$ |
|---|---|---|
| r1 | 0.9, 0.8, 0.3 | 0.900, 0.720, 0.216 |
| r2 | 0.7, 0.2 | 0.700, 0.140 |
| r3 | 0.4 | 0.400 |

SPS 表（光滑曲线）：$\mathrm{SPS}(1..9)=1.00,\ 0.95,\ 0.90,\ 0.85,\ 0.78,\ 0.70,\ 0.62,\ 0.54,\ 0.45$

贪心路径：

| 步 | 录取 | $B$ | $\tau$ | $\mathrm{SPS}(B)$ | $\Theta$ | 结果 |
|---|---|---|---|---|---|---|
| 初始 | — | 3 | 3.0000 | 0.90 | 2.7000 | — |
| 1 | r1 位置1（$a$=0.9） | 4 | 3.9000 | 0.85 | 3.3150 | 涨，收 |
| 2 | r1 位置2（$a$=0.72） | 5 | 4.6200 | 0.78 | 3.6036 | 涨，收 |
| 3 | r2 位置1（$a$=0.7） | 6 | 5.3200 | 0.70 | **3.7240** | 涨，收 ← 峰值 |
| 4 | r3 位置1（$a$=0.4） | 7 | 5.7200 | 0.62 | 3.5464 | **掉 → 停** |

最优解 $\ell^*=(2,1,0)$，$\Theta=3.7240$。

值得注意的是第 4 步：r3 的 $a=0.4$ 其实不算低，但录取它要把 $B$ 从 6 撑到 7，$\mathrm{SPS}$ 从 0.70 掉到 0.62——**多赚的 0.4 个 token 换不回引擎每秒少跑的 0.08 步**。这就是"verify smarter, not longer"的算术含义。

**七、实际部署里不是早停**

注意上面整套推导有个前提：$\mathrm{SPS}(B)$ 是光滑单峰的。论文 §5.2 说真实硬件不是这样——真实的 $\mathrm{SPS}(B)$ 是**离散、锯齿状阶梯下降**的，会破坏单峰性。

所以生产环境做了两处改动：

1. **去掉早停，改成无约束的全局搜索**，以免被锯齿状悬崖困在局部最优。
2. **用两步之前的置信度输出来估即将到来的验证容量 $K$**。这里有个分工要记清楚：**排序仍然用当前实时的置信度，历史预测只用来定截断长度**。

第 2 点不只是工程妥协。因为置信度头依赖前一个草稿 token（它的输入里含 $W_1[x_{k-1}]$），如果调度器跑完整趟搜索再回头决定"第一个位置收不收"，就等于偷看了第一个位置采出了什么，这会破坏无损性。**而这个两步的时间偏移恰好让决策只依赖更早的信息，绕开了这个问题。**

**八、悬置的一点**

论文说去掉早停是因为"锯齿状 SPS 悬崖"会让调度器卡在局部最优。由于我没有实际硬件的原因，所以说没办法验证这一点。

**九、跟真实硬件的距离**

上面整套贪心和理论推导，都**不直接面对真实场景里的 GPU graph、ZOS 这些执行层约束**。DSpark 实战用的是无约束全局搜索 + 前两步的历史预测（见 §5.2）。

**十、STS：置信度头为什么必须校准**

**为什么必须校准。** 论文给了一个明确对比：以前的阈值式方法只需要置信度**排序正确**（分高的排前面，门限卡在哪大致对就行）；而 DSpark 的调度器需要累乘值 $a_{r,j}$ 的**绝对数值准确**，因为 $\tau$ 是拿这些数值算出来、再乘 $\mathrm{SPS}$ 去比大小的。

数值偏高会怎样：假设真实存活概率是 $0.5$，但头报出 $0.9$，调度器就以为"这个 token 有九成希望活下来，值得占一个 batch 名额"，于是把 $B$ 撑大、把 $\mathrm{SPS}$ 拖下来——结果这个 token 一半概率被拒，**赚的还不够赔的**。

而神经网络输出的置信度天生过自信（论文引 Guo et al. 2017、Ovadia et al. 2019）。论文图 6 给了证据：模型辨别力很强（ROC-AUC 0.81–0.90，排序很准），但 ECE 高达 3%–8%（数值偏高）。**排序没问题，数值要修。**

**怎么做。** 用一份留出的验证集，从左往右、一个位置一个位置地标。对位置 $k$ 引入温度 $T_k$：

$$\hat{c}_k=\sigma\!\left(\frac{\mathrm{logit}(c_k)}{T_k}\right),\qquad \mathrm{logit}(c)=\ln\frac{c}{1-c}$$

处理位置 $k$ 时，前面 $1\dots k-1$ 的 $T_i$ 已经定好、冻结不动；只对 $T_k$ 做一维网格搜索，目标是让**累乘值** $\prod_{i\le k}\hat{c}_i$ 的 ECE 最小。标完 $k$ 再进 $k+1$。效果是平均 ECE 从 3%–8% 降到约 1%（图 6）。

**为什么标的是累乘值，不是单个 $c_k$。** 三层理由：

1. **调度器用的就是累乘值。** $\tau$ 里出现的每一项都是 $a_{r,j}=\prod_{i\le j}c_{r,i}$。校准要对准下游真正使用的那个量；如果只把每个单独的 $c_k$ 标到"平均等于经验条件接受率"，误差乘起来仍然会偏。
2. **链式法则要求逐位置保持"条件概率"的含义。** $c_k$ 定义成"前 $k-1$ 位都被接受的前提下，第 $k$ 位能活"，联合概率才等于这些条件概率相乘：$a_k=\prod_{i\le k}c_i$。如果只标最终乘积、不管中间，中间那些量就不再是条件概率，链式结构断掉，也就失去"每个位置单独可解释"这个性质。所以必须逐位置做。
3. **逐位置把 $\gamma$ 维搜索拆成 $\gamma$ 个一维搜索。** 理论上可以对 $T_1,\dots,T_\gamma$ 做联合网格搜索，但那是 $\gamma$ 维（$\gamma$ 最大到 16），代价爆炸。顺序做法代价线性，**代价是不保证全局最优**——前面位置的温度定死后，后面只能将就。

**为什么标完排序不变。** 对同一个位置 $k$，$T_k$ 是一个正常数，变换链是"$\mathrm{logit}$ → 除以 $T_k$ → $\sigma$"，三步都是严格单调递增的，复合起来整体保序。而且 $T_k$ 是逐位置的，位置 $k$ 的变换不影响位置 $j\ne k$ 的排序——**同一深度上的候选之间怎么排完全没被动过**。所以置信度头学到的"哪个 token 更值得信"一点没丢；**排序交给头，刻度交给校准器**。

**数值例子。** 造一个"系统性偏高"的例子：位置 1 平均报 0.80（真实 0.60），位置 2 平均报 0.60（条件真实 0.60）。

| 量 | 数值 |
|---|---|
| 真实联合（前两位全活） | $0.60\times0.60=0.36$ |
| 原始累乘预测 | $0.80\times0.60=0.48$ ← 偏高 33% |
| 网格搜索出的 $T_1$ | 2.36 |
| ECE（位置 1） | 0.1575 → **0.0003** |
| 网格搜索出的 $T_2$ | 0.90 |
| 标定后累乘 | 0.3926（对照验证集经验联合 0.3925） |
| ECE（累乘，位置 2） | 0.0875 → **0.0001** |

三件值得记住的事：

1. **STS 对齐的是"验证集上的经验值"，不是"真实值"。** 上例中真实条件接受率是 0.60，但随机抽样造出的验证集经验值是 0.6425，STS 把预测标到 0.6428——贴的是经验值。这不是 bug：校准器只能看到验证集，验证集规模决定校准精度上限。**以后自己做实验若要校准，验证集的构造方式和规模会直接进结果。**
2. **逐位置搜索会自动照顾"标定不足"的情况。** $T_2=0.90<1$，意味着这个位置模型是**不够自信**的，STS 把它往自信方向推。所以"过自信 → 降温"只是最常见情形，不是唯一情形。
3. **位置 2 的温度在补偿位置 1 的误差。** 标 $T_2$ 时 $T_1$ 已冻结，而 $T_2$ 的优化目标是累乘值 $\hat{c}_1\hat{c}_2$ 的 ECE——所以不管 $T_1$ 标得好不好，$T_2$ 都会尽力让"两个乘起来"贴近经验值。这是它能把 ECE 从 0.0875 压到 0.0001 的原因；只标单个 $c_2$ 做不到。

**这套方法的两个局限**（原文没明说，从方法本身看得出）：

1. **一个位置只有一个标量温度，只能修系统性偏差。** 如果可靠性图形状是"两头准、中间偏"这种非单调畸变，一个温度修不了。论文图 6 标定后 ECE 降到约 1%、不是 0，剩下的那 1% 大概就是这类修不掉的部分。
2. **逐位置贪心不保证全局最优**（理由见上面第 3 条）。理论上存在"$T_1$ 稍差、$T_2$ 就能好很多"的组合被顺序结构排除掉了。**这是拿最优性换可行性。**

## 硬件感知前缀调度器在生产环境中的实际形态（§5）

**两个冲突**

理论版 Algorithm 1 有两个前提，在真实基础设施上都不成立：

1. **容量曲线的假设不成立**：算法假设 $\mathrm{SPS}(B)$ 是光滑单峰的，实际是**离散、锯齿状阶梯下降**的。这破坏单峰假设，会让调度器卡在局部最优。
2. **执行框架不兼容**：算法要求每一步动态决定草稿 token 数，而这跟 **CUDA graph 连续重放**和 **Zero-Overhead Scheduling (ZOS)** 冲突——后两者要求形状 / 批大小固定，且下一步的批大小必须在当前步结束之前就知道。

**DSpark 的应对：用一点时间偏移换因果性**

- 去掉早停、改成无约束全局搜索，以免被锯齿状悬崖困在局部最优
- 用**两步之前**的置信度输出来估即将到来的验证容量 $K$
- 关键分工：**排序仍然用当前实时置信度，历史预测只用来定截断长度**

这个两步的时间偏移不只是工程妥协——它恰好让准入决策与当前 token 的实现隔离开，所以改成全局搜索之后，附录 A 那个"偷看未来"的问题依然不会出现。

**值得注意的点（我认为这是这一节最重要的收获）**

硬件感知调度器**本身就是在做预测**，只不过它预测的是硬件容量（SPS 曲线，离线 profile 得到），而不是网络状况。这说明"预测"在这类系统里不是新东西——DSpark 面对的是一个相对稳定的数据中心硬件，尚且需要用预测兜住波动；那网络侧的不确定性只会更大。

**工程代价（一个提醒）**

动态调度不是加个 if 就行。变长验证前缀跟标准解码 kernel 不兼容（标准 kernel 为固定 query 长度优化，直接跑会因 padding 和负载不均浪费 GPU）。DSpark 的解法是**把物理执行与逻辑序列追踪解耦**：所有请求的所有 token 拉平、当独立元素处理，序列内的依赖关系靠一个 **marker tensor** 在稀疏注意力里传递；在 DeepSeek-V4 上只需改 index-attention 和 compress 两个 kernel。

也就是：**物理层看到的是一堆等价的、无结构的 token，逻辑层的因果关系靠额外元信息还原。**

**帕累托前沿（图 7）**

帕累托前沿就是"无法在不牺牲一个指标的前提下改进另一个指标"的那条边界。图 7 横轴是聚合吞吐（token/s/gpu），纵轴是单用户生成速度（tok/s/user）；散点是真实流量采到的原始遥测数据，实线是拟合出的前沿。DSpark 的前沿在基线（MTP-1）外侧——同一个单用户速度下能给出更高聚合吞吐，这就叫"把前沿向外推"。

- **要小心的数字**：严格 SLA 锚点下的 +661% / +406%。**论文自己说了**，那是因为基线在那个点位已接近崩溃、并发只能开到很小，相对倍数才显得巨大，不应作为代表性加速比

## 离线实验（§4）

**本节的作用**

§3 讲机制，§4 提供机制的**证据**：DSpark 比现有草稿器好多少、好在哪、代价多少。

（说明：这一节的数据是我请 agent 代读并逐项核对过原文数字的，因为我自己对数据不敏感。核对方式：从论文 PDF 里提取表 1 原始数据、重算 macro-average，再跟论文声明的百分比对拍。）

**实验设置（§4.1）**

- **四个 target 模型**：Qwen3-{4B, 8B, 14B}、Gemma4-12B
- **两个基线**：Eagle3（自回归草稿器代表）、DFlash（并行草稿器代表）
- **公平性措施**：所有草稿器在同一训练框架、同一数据上**重新训练**；Eagle3 的 TTT horizon 与块大小对齐（都是 7）；层数上 Eagle3 是 1 层，DSpark 与 DFlash 都是 5 层
- **训练数据**：Open-PerfectBlend（130 万条），只取 prompt，回复由各自 target 模型重新生成；训练 10 epoch
- **评测域**：数学（GSM8K/MATH500/AIME25）、代码（MBPP/HumanEval/LiveCodeBench）、日常对话（MT-Bench/Alpaca/Arena-Hard）
- **指标**：每轮接受长度 $\tau$，越大越好
- **⚠️ 关键设置**：**离线评测把置信度调度器关掉了**，强制所有草稿器提固定长度的块。目的是把"草稿质量"和"调度策略"分开。**所以表 1 的数字全部只反映草稿质量，跟调度器无关**；调度器的收益要到 §5 的生产数据才看得到。

**主结果（表 1）**

| target | Eagle3 | DFlash | DSpark | vs Eagle3 | vs DFlash |
|---|---|---|---|---|---|
| Qwen3-4B | 3.611 | 4.064 | **4.727** | +30.9% | +16.3% |
| Qwen3-8B | 3.798 | 4.067 | **4.813** | +26.7% | +18.4% |
| Qwen3-14B | 3.676 | 4.039 | **4.779** | +30.0% | +18.3% |
| Gemma4-12B | 4.376 | 4.018 | **4.663** | +6.6% | +16.1% |

（前三行的百分比我逐项重算过，与论文声明完全一致。Gemma4-12B 论文只说了"跨模型族优势一致"，没给具体百分比，这里的数字是按同样方法算的。）

**两个要记住的数字**：

1. **+16%～18%（对 DFlash）**——这是**半自回归机制单独的净收益**，因为 DSpark 和 DFlash 用的是同一个并行 backbone。这是半自回归这一层设计的定价。
2. **+27%～31%（对 Eagle3）**——这是"深度并行 backbone 的相对优势"加"半自回归"合起来的效果。

**逐领域：强领域效应（§4.2）**

以 Qwen3-4B 为例，逐领域平均：

| 域 | Eagle3 | DFlash | DSpark |
|---|---|---|---|
| 数学（GSM8K/MATH/AIME25） | 4.56 | 4.80 | **5.57** |
| 代码（MBPP/HumanEval/LCB） | 3.87 | 4.44 | **5.12** |
| 对话（MT-Bench/Alpaca/Arena） | 2.40 | 2.95 | **3.49** |

数学和代码的接受长度天然远高于开放对话。这就是"固定验证长度会浪费算力"的直接动机——对话任务上尾部 token 大量注定被拒，却还得每个都验。

**为什么并行反而比自回归好：逐位置接受率（§4.3.1，图 2）**

这是全文最关键的一张图，它把"并行草稿器到底哪里坏了"画出来了。

它统计的是**条件接受率**：对位置 $k$，分母只算"前 $1$ 到 $k-1$ 位全部被接受"的样本，再看这些样本里位置 $k$ 也被接受的比例。这样就把前面拒绝的惩罚剥掉，只看每个位置本身的预测质量。

结论分三段：

1. **位置 1 上并行草稿器赢，赢在容量。** 位置 1 所有架构都只看目标上下文，差距纯粹来自网络容量：自回归模型因 $T_{\text{draft}}\propto\gamma$ 被迫做浅，并行的可以深。DFlash 起点明显高于 Eagle3——数学 0.88 vs 0.81，对话 0.72 vs 0.53。
2. **位置 1 的杠杆最大。** 投机解码是严格前缀存活，位置 1 一被拒整个块全废。所以位置 1 的容量优势会被不成比例地放大到最终接受长度——这解释了为什么并行草稿器宏观上能赢自回归。
3. **越往后并行越吃亏。** 前面的 token 锁定语义路径后，后面的本来该更好预测。Eagle3 吃到了这个确定性（对话上从 0.53 **升到** 0.74），DFlash 却**衰减**（代码 0.87→0.78，对话 0.72→0.63）。论文归因于**多模态碰撞**：并行位置是对所有可能前驱做边际化，而不是以实际采到的那条前缀为条件，容易给出互相矛盾的组合。

DSpark 就是冲着这两条来的：用深度并行 backbone 拿下位置 1 的高起点（数学 0.93），再用轻量顺序头压住衰减，让整块保持高而稳定的条件接受率。

**代价分析：深度与块长（§4.3.2，图 3、图 4）**

**深度**：块大小固定 7，DSpark 层数从 1 加到 5。性能单调上升，**1→2 层收益最陡**，而且 **2 层 DSpark 在所有域上都超过 5 层 DFlash**。论文解读：靠轻量顺序头注入局部自回归，比单纯堆并行层数在"精度-参数量"上更划算。

**块长**：层数固定 5，块长（含锚 token）扫 {4, 8, 12, 16}。

| 域 | $\gamma=7$ 时对 DFlash 的提升 | $\gamma=15$ 时 |
|---|---|---|
| 数学 | +16% | **+30%** |
| 代码 | +15% | **+26%** |
| 对话 | +18% | **+22%** |

**优势随块长增大而扩大**——纯并行的边际效用随块长递减，DSpark 压住了衰减，所以块越长相对越占优。**这意味着"用更大的块"在半自回归架构下才真正划得来。**

**时延开销**：图 4 最右。全轮时延 = 一次目标验证 + 并行草稿前向 + 串行采样循环，batch size 128，上下文长度取 {512, 1024, 2048, 4096} 的算术平均。**块长从 4 扩到 16，只给全轮时延增加 0.2%～1.3%**（相对 DFlash 基线），因为该 batch size 下目标模型主导验证计算时间。**换来的是最多 +30% 的接受长度。**

**置信度头的单独验证（§4.3.3，图 5）**

用**静态阈值扫描**做诊断：阈值从 0 往上调，看接受率与每步 token 数怎么变。阈值 0 等于标准固定长度验证。

| 域 | 接受率（阈值 0 → 高阈值） |
|---|---|
| 对话 | 45.7% → **95.7%** |
| 数学 | 76.9% → 92.5% |
| 代码 | 67.6% → 92.0% |

**对话任务的剪枝最剧烈**（45.7→95.7），因为它 token 分布熵更高、固定长度验证最浪费；数学和代码剪得少、保留草稿更多。

这一节是**隔离验证**：证明置信度头确实能识别该丢的 token。调度器的评估被明确放到 §5 生产环境。

**校准质量（图 6）**

- 原始置信度头：辨别力强（ROC-AUC 0.81–0.90），但过自信（ECE 3%–8%）
- STS 校准后：平均 ECE 降到约 1%
- 逐位置：位置 1 ECE 5.7%→2.0%，位置 3 8.2%→1.7%，位置 5 5.8%→0.8%，位置 7 3.3%→0.4%

**这一节最重要的一条**：对话域的 45.7%→95.7% 说明"剪掉注定被拒的 token"在**高熵任务**上收益最大——高熵场景的 token 分布更散，固定长度验证最浪费。
