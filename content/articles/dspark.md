传统投机解码的核心思想是使用 draft 模型先自回归生成一定量的 token 作为草稿，然后由 target 模型做前向传播验证比对接受，一旦不接受，后面舍弃。每个 token 的生成时延就等于 $(T_{\text{draft}} + T_{\text{verify}})/\tau$。

要降低时延，就有三个关键点：降低草稿生成时间、降低验证时间、增加接受 token 数量。

过去的解决方案，如 DFlash 采用了并行草稿生成器来降低草稿生成时间，但并行不依赖于前缀，导致后缀的接受率会出现灾难性的崩塌。

DSpark 的核心设计就是同时优化这三者，用两条措施覆盖三个关键点：半自回归生成器同时降低草稿生成时间并提高接受长度；置信度调度验证让 target 模型可以并行验证置信度，从而减少验证时间。

## 1 半自回归生成

### 1.1 草稿器吃的是 token 还是特征

在展开半自回归之前，有一个容易被跳过、但决定了整个系统成本结构的问题：**草稿器（drafter）到底拿什么当输入？**

按这个标准，草稿器分成两个接口族。

**token 级接口**：草稿器只消费已经确定的 token，自己靠一个独立的小模型往前推。Eagle3 是这一族的代表，它逐位置生成、每个位置条件在之前采出的 token 上，但**不接受 target 的任何内部表示**。

**特征级接口**：草稿器消费 target 的**隐状态**。DFlash 是这一族的代表——在 prefill 阶段把 target 若干层的隐状态取出、拼接、投影进草稿器的隐空间：

$$H_{\text{ctx}}=\mathrm{RMSNorm}\bigl(W_c\,[H^{(l_{1})};\,\ldots;\,H^{(l_{m})}]\bigr)$$

然后这些上下文特征被注入草稿器的每一层：把它们与草稿块的表示沿 key 和 value 的序列维度拼接起来。也就是说，草稿器每一步都在"看着 target 的内部表示"起草。顺带一提，草稿器还共享 target 的 embedding 层和 LM head（两者都冻结）。

这个区分直接决定成本结构。token 级接口的跨设备部署在数据面上更省事——传 token 就够，草稿器不需要看到 target 的内部状态（至于它自己的参数和 KV 怎么摆，是另一个问题）。特征级接口则天然要求 target 的隐状态**流到草稿器手里**，这笔开销在单机内是显存带宽，一旦草稿器与 target 不共置，它就变成网络带宽。

DSpark 属于后者：它的并行 backbone 直接建在 DFlash 上，继承了整套 KV 注入机制。

### 1.2 并行出 logits、串行采样、顺序偏置

半自回归生成的核心，是先用并行前向传播把整个 draft 块的 logits 一次性算出来，再从左往右逐个采样，并在采样时注入顺序偏置。

这里要区分清楚两步：并行阶段产出的是各个位置的 logits（也就是每个位置一整套概率分布），并没有真正定下 token；真正的 token 是在顺序阶段从左往右采出来的。因为并行阶段每个位置是对所有可能前驱做边际化，而不是以实际采到的那个前驱为条件，块内越靠后越容易采出互相矛盾的组合，接受率会快速衰减。顺序偏置补的正是这个缺失的条件依赖：每采一个 token，就把前文采出的 token 所造成的偏置加进当前分布，让后面的 token 真的知道前面采了什么。

这就是"半"自回归的由来：$T_{\text{sequential}} \ll T_{\text{parallel}}$。

顺序偏置可以有不同的实现复杂度。最简单的一档是让它只看前一个 token，也就是下面这个 markov 头。

### 1.3 Markov 头与低秩分解

Markov 头是最简单的实现方式：只让偏置依赖前一个 token。

$$B(x_{k-1},\cdot) = W_1[x_{k-1}]\,W_2 \in \mathbb{R}^{\mathcal{V}}$$

原则上这是一个完整的 $\mathcal{V}\times\mathcal{V}$ 转移矩阵：行是前一个 token（$\mathcal{V}$ 种可能），列是正在预测的 token，第 $x_{k-1}$ 行就是"上一个 token 是 $x_{k-1}$ 时，给所有候选 token 各加多少偏置"。但 $\mathcal{V}\approx 10^5$ 时 $\mathcal{V}^2$ 有 $10^{10}$ 个数，存不下也算不动，所以做低秩分解 $B = W_1W_2$：$W_1$ 是 $\mathcal{V}\times r$，每个 token 对应一行 $r$ 维的"身份码"；$W_2$ 是 $r\times\mathcal{V}$，把身份码投影成 $\mathcal{V}$ 维偏置。$r$ 默认 256，参数量从 $10^{10}$ 降到约 $5\times 10^7$。用的时候就是查表（取 $W_1$ 的第 $x_{k-1}$ 行）再投影，所以每步只是一次查表加一个 $256\times 10^5$ 的矩阵乘，非常轻量。

代价是：$W_1W_2$ 的秩最多是 256，所有行的偏置被压进同一个 256 维子空间，不可能各行独立。这里赌的是 token 之间的转移偏好本身存在大量冗余、可用低维表达，属于经验上的近似，不是无损。

### 1.4 RNN 头为什么默认不用

RNN 头让状态累积整块历史，不受"只看前一个"的限制，但要维护循环状态、实现更复杂、部署性质也更差，而原作实测它相对 Markov 头只有很小的额外收益，所以默认不用它。

## 2 置信度调度验证

置信度头负责"给数"：对草稿块里的每一个位置，估计这个 token 能活过验证的概率。

硬件感知前缀调度器负责"用数"：拿这些概率，结合当前硬件负载，决定这一步实际验证多少个 token。

置信度头不参与决策，调度器不做预测，**头给数、调度器用数**，耦合点就在这。

### 2.1 调度器本质上是资源调度

调度器其实不只是"决定验证多长"，它本质上是在做**资源调度**——按存活概率从高到低排序候选 token，然后在容量预算内取一个 top-K。这个容量预算就是 batch 容量，而 batch 容量和引擎每秒能跑多少步的关系，就是论文里那条 SPS 曲线（SPS：batch 里有 $B$ 个 token 时引擎每秒能跑几步），它是提前 profile 出来的。

### 2.2 理论和生产实现之间隔着两道坎

到这里机制就讲完了，但理论版的算法没法直接上生产：它有两个前提在真实基础设施上都不成立，一个是容量曲线并不光滑，一个是动态长度跟执行框架不兼容。这两条决定了 DSpark 的调度器在生产环境里长成什么样，代价不小。先把它们记在这里，具体的推导和应对放到第 3 节末尾和第 4 节展开。

## 3 调度器怎么算

置信度头把每个草稿位置的存活概率给出来之后，调度器要做的决策就很具体：为每个活跃请求挑一个验证长度 $\ell_r$，把这一批候选 token 送进 target 模型验证。多验一个位置不止多赚一点期望 token，还会把这一步的 batch 撑大、把引擎每秒能跑的步数压下去，所以定长度不是拍脑袋的事，而是一道能完整写出来的最优化问题。这一节把它从头算一遍。

### 3.1 四个量

设 $R$ 是活跃请求数，$\gamma$ 是草稿块可验证位置数的上限，调度器给请求 $r$ 定的验证长度 $\ell_r$ 取 $0$ 到 $\gamma$ 之间的整数。$c_{r,i}$ 是置信度头输出的第 $i$ 个位置的条件存活概率——"前面几位都活着"的前提下，第 $i$ 位能活下来的概率。$\mathrm{SPS}(B)$ 沿用第 2.1 节的定义：batch 里有 $B$ 个 token 时引擎每秒能跑几步，这张小表在引擎初始化时离线 profile 一次，之后查表用。

四个量依次是：

$$a_{r,j}=\prod_{i\le j}c_{r,i}$$

前缀存活概率——请求 $r$ 的第 $1$ 到第 $j$ 个草稿位置全部被接受的概率，由条件存活概率逐位置累乘得到。

$$B=\sum_{r=1}^{R}(1+\ell_r)$$

这一步送进 target 模型的 token 数，$R$ 个请求各自贡献 $1+\ell_r$ 个。

$$\tau=\sum_{r=1}^{R}\Big(1+\sum_{j=1}^{\ell_r}a_{r,j}\Big)$$

这一步期望能收下的 token 数。

$$\Theta=\tau\cdot\mathrm{SPS}(B)$$

系统每秒产出的 token 数，也就是要最大化的目标。

### 3.2 $\tau$ 为什么长这样

$\tau$ 由两部分组成。

第一部分是**保底收获**。哪怕一个草稿都不验（$\ell_r=0$），target 模型跑一次前向也会从自己的分布里采一个 token 输出，这一个必定到手。$R$ 个请求就是 $R$ 个，这就是式子里那个 $\sum_r 1$。

第二部分是**草稿的期望收获**。第 $j$ 个草稿位置能不能被收下，要求"前面 $1$ 到 $j-1$ 位全部被接受，且第 $j$ 位自己也被接受"——因为投机解码只接受连续前缀。而这件事的概率恰好就是 $a_{r,j}$，因为 $c_{r,i}$ 的定义就是"前面都活着的前提下，第 $i$ 位能活"这个条件概率。所以直接用期望的线性性，把 $\ell_r$ 个概率加起来就行，**不需要各位置相互独立**。

也可以用另一种方式验证：记"恰好收下 $k$ 个草稿"的概率是 $a_k(1-c_{k+1})$，对 $k$ 求期望再做一遍分部求和，会塌成 $\sum_j a_j$，结果一致。

### 3.3 $\Theta$ 为什么是乘

$$\underbrace{\tau}_{\text{每步收几个 token}}\times\underbrace{\mathrm{SPS}(B)}_{\text{每秒跑几步}}=\underbrace{\Theta}_{\text{每秒产几个 token}}$$

量纲上是自洽的：每步收到多少 token，乘以每秒能跑多少步，就是每秒产出多少 token。这就是系统总吞吐——GPU 每秒能给所有用户吐出多少 token。

调度器的任务因此清楚：$\ell_1,\dots,\ell_R$ 是要选的量。多验一点，$\tau$ 涨，但 $B$ 涨、$\mathrm{SPS}$ 跌。**要在"多赚的 token"和"每秒少跑的步"之间找平衡。**

### 3.4 为什么可以贪心

贪心成立的根据只有一条：**把请求 $r$ 的验证长度从 $j-1$ 延到 $j$，期望接受 token 的增量恰好是 $a_{r,j}$。**

因为 $\tau$ 里位置 $j$ 的贡献就是 $a_{r,j}$，加上去就多这么多，没有别的耦合项。

而 $a_{r,j}$ 对 $j$ **单调不增**（累乘只会越乘越小）。这一条带来两个后果：

1. **块内前缀依赖自动被满足**。你不可能"跳过位置 2 只验位置 3"。而把所有请求的所有候选位置按 $a_{r,j}$ 全局排序后，同一请求的位置天然按 $j=1,2,3\dots$ 的顺序出现，所以取排序列表的前缀永远不会出现非法跳跃。
2. **每个候选的成本都一样**（都是往 batch 里加 1），所以只比收益就够了。如果总预算 $B$ 固定，最优解就是取收益最大的那 $B$ 个——也就是排序列表的前缀。

算法因此长这样：初始让所有 $\ell_r=0$（$B=R$，$\tau=R$），然后沿排序列表依次录取，每录取一个就更新 $B$ 和 $\tau$、重算 $\Theta$，**一旦 $\Theta$ 下降就停**。

### 3.5 单峰性——早停为什么有效，以及它的条件

早停能工作，靠的是 $\Theta$ 沿这条路径**先升后降**（单峰）。论文的措辞是 if and only if：逐步早停能取到全局最优吞吐，**当且仅当** $\Theta$ 是单峰的。这个结论是在光滑曲线假设下论证的，而真实硬件的曲线并不光滑——这一点直接决定了生产环境为什么不用早停。

那单峰又靠什么？靠**收益的衰减速度压过 SPS 的波动幅度**。

记第 $k$ 步的边际收益是 $g_k$（就是那一格候选的 $a$ 值），SPS 从 $B$ 到 $B+1$ 的比值是 $\rho_k=\mathrm{SPS}(B+1)/\mathrm{SPS}(B)$。要让 $\Theta$ 的增量一路递减，核心要求是 $g_k$ 掉得够快、或者 $\rho_k$ 波动够小。光滑曲线之所以安全，是因为它的 $\rho_k$ 每步都接近 1，被 $g_k$ 的衰减稳稳压住。

**所以"光滑"是充分条件，不是根本条件。** 根本条件是上面那条衰减关系。

### 3.6 数值例子

三个请求，$\gamma$ 分别是 3、2、1：

| 请求 | $c_{r,1},c_{r,2},c_{r,3}$ | $a_{r,1},a_{r,2},a_{r,3}$ |
|---|---|---|
| r1 | 0.9, 0.8, 0.3 | 0.900, 0.720, 0.216 |
| r2 | 0.7, 0.2 | 0.700, 0.140 |
| r3 | 0.4 | 0.400 |

SPS 表（光滑曲线）：$\mathrm{SPS}(1..9)=1.00,\ 0.95,\ 0.90,\ 0.85,\ 0.78,\ 0.70,\ 0.62,\ 0.54,\ 0.45$

贪心路径：

| 步 | 录取 | $B$ | $\tau$ | $\mathrm{SPS}(B)$ | $\Theta$ | 结果 |
|---|---|---|---|---|---|---|
| 初始 | — | 3 | 3.0000 | 0.90 | 2.7000 | — |
| 1 | r1 位置1（$a$=0.9） | 4 | 3.9000 | 0.85 | 3.3150 | 涨，收 |
| 2 | r1 位置2（$a$=0.72） | 5 | 4.6200 | 0.78 | 3.6036 | 涨，收 |
| 3 | r2 位置1（$a$=0.7） | 6 | 5.3200 | 0.70 | **3.7240** | 涨，收 ← 峰值 |
| 4 | r3 位置1（$a$=0.4） | 7 | 5.7200 | 0.62 | 3.5464 | **掉 → 停** |

最优解 $\ell^*=(2,1,0)$，$\Theta=3.7240$。

值得注意的是第 4 步：r3 的 $a=0.4$ 其实不算低，但录取它要把 $B$ 从 6 撑到 7，$\mathrm{SPS}$ 从 0.70 掉到 0.62——**多赚的 0.4 个 token 换不回引擎每秒少跑的 0.08 步**。这就是论文那句 "verify smarter, not longer"（更聪明地验，而不是验得更长）的算术含义。

顺便说清一件事：这个例子全程单峰，第 4 步只是正常的下探，早停在这里完全有效。它不是"锯齿让早停出错"的反例——要构造那种反例，曲线得在下降之后出现足够大的反弹（这一点在第 5 节还会回到）。

### 3.7 生产环境里为什么不是早停

上面整套推导有个前提：$\mathrm{SPS}(B)$ 是光滑单峰的。论文说真实硬件不是这样——真实的 $\mathrm{SPS}(B)$ 是**离散、锯齿状阶梯下降**的，会破坏单峰性。

所以生产环境做了两处改动：**去掉早停，改成无约束的全局搜索**，以免被锯齿状悬崖困在局部最优；并且**用两步之前的置信度输出来估即将到来的验证容量 $K$**，其中**排序仍然用当前实时的置信度，历史预测只用来定截断长度**。

第二处改动不只是工程妥协。因为置信度头依赖前一个草稿 token（它的输入里含 $W_1[x_{k-1}]$），如果调度器跑完整趟搜索再回头决定"第一个位置收不收"，就等于偷看了第一个位置采出了什么，这会破坏无损性。**而这个两步的时间偏移恰好让决策只依赖更早的信息，绕开了这个问题。**

至于这两个前提具体怎么跟硬件和执行框架冲突、要付什么工程代价，是下一节的事。

## 4 实验证据

前面讲的是机制：深度并行 backbone、半自回归、置信度头。机制讲得再顺，也要有数字兜底。这一节给的就是离线证据，我关心的三件事是：DSpark 比现有草稿器好多少、好在哪、代价多少。

### 4.1 实验设置

离线实验在四个 target 上做：Qwen3-{4B, 8B, 14B} 和 Gemma4-12B。基线选了两个，分别代表两类主流草稿器：Eagle3 代表自回归草稿器，DFlash 代表并行草稿器。

公平性是这些数字能不能信的前提，所以几条都对齐了：所有草稿器都在同一训练框架、同一份数据上重新训练；Eagle3 的 TTT horizon 与块大小对齐，都是 7；层数上 Eagle3 是 1 层，DSpark 与 DFlash 都是 5 层。训练数据用 Open-PerfectBlend（130 万条），只取 prompt，回复由各自的 target 模型重新生成，训练 10 epoch。评测覆盖三个域：数学（GSM8K/MATH500/AIME25）、代码（MBPP/HumanEval/LiveCodeBench）、日常对话（MT-Bench/Alpaca/Arena-Hard）。指标是每轮接受长度 $\tau$，越大越好。

有一条关键设置要先说清楚：离线评测把置信度调度器关掉了，强制所有草稿器提固定长度的块。这么做的目的是把"草稿质量"和"调度策略"分开。所以表 1 的数字全部只反映草稿质量，跟调度器无关；调度器能带来多少收益，要到生产环境的数据里才看得到。

### 4.2 主结果

| target | Eagle3 | DFlash | DSpark | vs Eagle3 | vs DFlash |
|---|---|---|---|---|---|
| Qwen3-4B | 3.611 | 4.064 | **4.727** | +30.9% | +16.3% |
| Qwen3-8B | 3.798 | 4.067 | **4.813** | +26.7% | +18.4% |
| Qwen3-14B | 3.676 | 4.039 | **4.779** | +30.0% | +18.3% |
| Gemma4-12B | 4.376 | 4.018 | **4.663** | +6.6% | +16.1% |

表 1 前三行的百分比按原始数据重算过，与论文声明一致。Gemma4-12B 那一行论文只说了"跨模型族优势一致"，没有给具体百分比，这里的数字是按同样方法算出来的。

有两个数字需要分开看：

1. **+16%～18%（对 DFlash）**——这是半自回归机制单独的净收益，因为 DSpark 和 DFlash 用的是同一个并行 backbone。这是半自回归这一层设计的定价。
2. **+27%～31%（对 Eagle3）**——这是"深度并行 backbone 的相对优势"加"半自回归"合起来的效果。

### 4.3 逐领域：强领域效应

以 Qwen3-4B 为例，逐领域平均：

| 域 | Eagle3 | DFlash | DSpark |
|---|---|---|---|
| 数学（GSM8K/MATH/AIME25） | 4.56 | 4.80 | **5.57** |
| 代码（MBPP/HumanEval/LCB） | 3.87 | 4.44 | **5.12** |
| 对话（MT-Bench/Alpaca/Arena） | 2.40 | 2.95 | **3.49** |

数学和代码的接受长度天然远高于开放对话。这正是"固定验证长度会浪费算力"的直接动机——对话任务上尾部 token 大量注定被拒，却还得每个都验一遍。

### 4.4 逐位置条件接受率（图 2）

这是全文最关键的一张图，它把"并行草稿器到底哪里坏了"画了出来。

图 2 统计的是条件接受率，口径要先说清：对位置 $k$，分母只算"前 $1$ 到 $k-1$ 位全部被接受"的样本，再看这些样本里位置 $k$ 也被接受的比例。前面拒绝带来的惩罚就这样被剥掉，剩下的只是每个位置本身的预测质量。

结论分三段。

第一，**位置 1 上并行草稿器赢，赢在容量**。位置 1 所有架构都只看目标上下文，差距纯粹来自网络容量：自回归模型因为 $T_{\text{draft}}\propto\gamma$ 被迫做浅，并行的可以深。DFlash 的起点明显高于 Eagle3——数学 0.88 vs 0.81，对话 0.72 vs 0.53。

第二，**位置 1 的杠杆最大**。投机解码是严格前缀存活，位置 1 一旦被拒整个块全废。所以位置 1 的容量优势会被不成比例地放大到最终接受长度，这解释了并行草稿器宏观上为什么能赢自回归。

第三，**越往后并行越吃亏**。前面的 token 锁定语义路径之后，后面的本来应该更好预测。Eagle3 吃到了这份确定性，对话上从 0.53 升到 0.74；DFlash 却在衰减，代码 0.87→0.78，对话 0.72→0.63。论文把原因归到多模态碰撞：并行位置是对所有可能前驱做边际化，而不是以实际采到的那条前缀为条件，容易给出互相矛盾的组合。

DSpark 就是冲着这两条来的：用深度并行 backbone 拿下位置 1 的高起点（数学 0.93），再用轻量顺序头（markov 头）压住越往后越严重的衰减，让整块保持高而稳定的条件接受率。

### 4.5 代价：深度、块长与时延

**深度**：块大小固定为 7，把 DSpark 的层数从 1 加到 5。性能单调上升，**1→2 层收益最陡**，而且 **2 层 DSpark 在所有域上都超过 5 层 DFlash**。论文的解读是：靠轻量顺序头注入局部自回归，比单纯堆并行层数在"精度-参数量"上更划算。

**块长**：层数固定为 5，块长（含锚 token）扫 {4, 8, 12, 16}。

| 域 | $\gamma=7$ 时对 DFlash 的提升 | $\gamma=15$ 时 |
|---|---|---|
| 数学 | +16% | **+30%** |
| 代码 | +15% | **+26%** |
| 对话 | +18% | **+22%** |

优势随块长增大而扩大。纯并行的边际效用随块长递减，DSpark 压住了这个衰减，所以块越长相对越占优——"用更大的块"在半自回归架构下才真正划得来。

**时延开销**：全轮时延 = 一次目标验证 + 并行草稿前向 + 串行采样循环。测量条件是 batch size 128，上下文长度取 {512, 1024, 2048, 4096} 的算术平均。块长从 4 扩到 16，只给全轮时延增加 0.2%～1.3%（相对 DFlash 基线），因为在这个 batch size 下验证计算时间由目标模型主导。换来的是最多 +30% 的接受长度。

### 4.6 置信度头的单独验证（图 5）

用静态阈值扫描做诊断：阈值从 0 往上调，看接受率与每步 token 数怎么变。阈值 0 就等于标准的固定长度验证。

| 域 | 接受率（阈值 0 → 高阈值） |
|---|---|
| 对话 | 45.7% → **95.7%** |
| 数学 | 76.9% → 92.5% |
| 代码 | 67.6% → 92.0% |

对话任务的剪枝最剧烈（45.7→95.7），因为它 token 分布熵更高、固定长度验证最浪费；数学和代码剪得少、保留的草稿更多。这一节是隔离验证，证明置信度头确实能识别该丢的 token；调度器本身的评估被明确放到生产环境去做。

### 4.7 校准质量（图 6）

原始置信度头辨别力强（ROC-AUC 0.81–0.90），但过自信（ECE 3%–8%）；经过 STS（对置信度头输出做的逐位置温度校准，具体做法见第 5 节）后，平均 ECE 降到约 1%。逐位置看：位置 1 从 5.7% 降到 2.0%，位置 3 从 8.2% 降到 1.7%，位置 5 从 5.8% 降到 0.8%，位置 7 从 3.3% 降到 0.4%。

这里有一条能独立成立的技术判断：对话域的 45.7%→95.7% 说明"剪掉注定被拒的 token"在高熵任务上收益最大。

### 4.8 生产环境：两个冲突与执行层应对

回到第 2.2 节留下的那两道坎。

一是**容量曲线的假设不成立**：算法假设 $\mathrm{SPS}(B)$ 是光滑单峰的，实际却是离散、锯齿状阶梯下降的。这破坏了单峰假设，会让调度器卡在局部最优。这也是第 3.7 节那把早停换成全局搜索的原因。

二是**执行框架不兼容**：算法要求每一步动态决定草稿 token 数，而这跟 CUDA graph 连续重放和 Zero-Overhead Scheduling (ZOS) 冲突——后两者要求形状 / 批大小固定，而且下一步的批大小必须在当前步结束之前就知道。

工程代价上，动态调度不是加个 if 就行。变长验证前缀跟标准解码 kernel 不兼容——标准 kernel 为固定 query 长度优化，直接跑会因为 padding 和负载不均浪费 GPU。DSpark 的解法是把物理执行与逻辑序列追踪解耦：所有请求的所有 token 拉平、当独立元素处理，序列内的依赖关系靠一个 marker tensor 在稀疏注意力里传递；在 DeepSeek-V4 上只需要改 index-attention 和 compress 两个 kernel。也就是说，物理层看到的是一堆等价的、无结构的 token，逻辑层的因果关系靠额外元信息还原。

### 4.9 帕累托前沿（图 7）

帕累托前沿就是"无法在不牺牲一个指标的前提下改进另一个指标"的那条边界。图 7 的横轴是聚合吞吐（token/s/gpu），纵轴是单用户生成速度（tok/s/user）；散点是真实流量采到的原始遥测数据，实线是拟合出来的前沿。DSpark 的前沿落在基线（MTP-1）的外侧——同一个单用户速度下能给出更高的聚合吞吐，这就是"把前沿向外推"。

数字要分成两档看。可信的对比是中等 SLA（80 与 35 tok/s/user）下的吞吐 +51% / +52%，以及同等吞吐下单用户速度 +60%～85%。要小心的是严格 SLA 锚点下的 +661% / +406%：论文自己说了，那是因为基线在那个点位上已经接近崩溃、并发只能开到很小，相对倍数才显得巨大，不应作为代表性的加速比。论文肯主动标注"这个数不代表性"，这一点本身值得记一笔。

## 5 置信度校准与遗留问题

### 5.1 置信度头为什么必须校准

论文给了一个明确对比：以前的阈值式方法只需要置信度**排序正确**——分高的排前面，门限卡在哪大致对就行；而 DSpark 的调度器需要累乘值 $a_{r,j}$ 的**绝对数值准确**，因为 $\tau$ 是拿这些数值算出来、再乘 $\mathrm{SPS}$ 去比大小的。

数值偏高会怎样：假设真实存活概率是 $0.5$，但头报出 $0.9$，调度器就以为"这个 token 有九成希望活下来，值得占一个 batch 名额"，于是把 $B$ 撑大、把 $\mathrm{SPS}$ 拖下来——结果这个 token 一半概率被拒，**赚的还不够赔的**。

而神经网络输出的置信度天生过自信（论文引 Guo et al. 2017、Ovadia et al. 2019）。第 4.7 节的数字也印证了这点：模型辨别力很强（ROC-AUC 0.81–0.90，排序很准），但 ECE 高达 3%–8%（数值偏高）。**排序没问题，数值要修。**

### 5.2 STS：逐位置温度校准

做法是：用一份留出的验证集，从左往右、一个位置一个位置地标。对位置 $k$ 引入温度 $T_k$：

$$\hat{c}_k=\sigma\!\left(\frac{\mathrm{logit}(c_k)}{T_k}\right),\qquad \mathrm{logit}(c)=\ln\frac{c}{1-c}$$

处理位置 $k$ 时，前面 $1\dots k-1$ 的 $T_i$ 已经定好、冻结不动；只对 $T_k$ 做一维网格搜索，目标是让**累乘值** $\prod_{i\le k}\hat{c}_i$ 的 ECE 最小。标完 $k$ 再进 $k+1$。效果就是第 4.7 节那个数字：平均 ECE 从 3%–8% 降到约 1%。

**为什么标的是累乘值，不是单个 $c_k$。** 三层理由：

1. **调度器用的就是累乘值。** $\tau$ 里出现的每一项都是 $a_{r,j}=\prod_{i\le j}c_{r,i}$。校准要对准下游真正使用的那个量；如果只把每个单独的 $c_k$ 标到"平均等于经验条件接受率"，误差乘起来仍然会偏。
2. **链式法则要求逐位置保持"条件概率"的含义。** $c_k$ 定义成"前 $k-1$ 位都被接受的前提下，第 $k$ 位能活"，联合概率才等于这些条件概率相乘：$a_k=\prod_{i\le k}c_i$。如果只标最终乘积、不管中间，中间那些量就不再是条件概率，链式结构断掉，也就失去"每个位置单独可解释"这个性质。所以必须逐位置做。
3. **逐位置把 $\gamma$ 维搜索拆成 $\gamma$ 个一维搜索。** 理论上可以对 $T_1,\dots,T_\gamma$ 做联合网格搜索，但那是 $\gamma$ 维（$\gamma$ 最大到 16），代价爆炸。顺序做法代价线性，**代价是不保证全局最优**——前面位置的温度定死后，后面只能将就。

**为什么标完排序不变。** 对同一个位置 $k$，$T_k$ 是一个正常数，变换链是"$\mathrm{logit}$ → 除以 $T_k$ → $\sigma$"，三步都是严格单调递增的，复合起来整体保序。而且 $T_k$ 是逐位置的，位置 $k$ 的变换不影响位置 $j\ne k$ 的排序——**同一深度上的候选之间怎么排完全没被动过**。所以置信度头学到的"哪个 token 更值得信"一点没丢：**排序交给头，刻度交给校准器**。

**一个数值例子。** 造一个"系统性偏高"的例子：位置 1 平均报 0.80（真实 0.60），位置 2 平均报 0.60（条件真实 0.60）。

| 量 | 数值 |
|---|---|
| 真实联合（前两位全活） | $0.60\times0.60=0.36$ |
| 原始累乘预测 | $0.80\times0.60=0.48$ ← 偏高 33% |
| 网格搜索出的 $T_1$ | 2.36 |
| ECE（位置 1） | 0.1575 → **0.0003** |
| 网格搜索出的 $T_2$ | 0.90 |
| 校准后累乘 | 0.3926（对照验证集经验联合 0.3925） |
| ECE（累乘，位置 2） | 0.0875 → **0.0001** |

三件值得记住的事：

1. **STS 对齐的是"验证集上的经验值"，不是"真实值"。** 上例中真实条件接受率是 0.60，但随机抽样造出的验证集经验值是 0.6425，STS 把预测标到 0.6428——贴的是经验值。这不是 bug：校准器只能看到验证集，验证集规模决定校准精度上限。以后自己做实验若要校准，验证集的构造方式和规模会直接进结果。
2. **逐位置搜索会自动照顾"校准不足"的情况。** $T_2=0.90<1$，意味着这个位置模型是**不够自信**的，STS 把它往自信方向推。所以"过自信 → 降温"只是最常见情形，不是唯一情形。
3. **位置 2 的温度在补偿位置 1 的误差。** 标 $T_2$ 时 $T_1$ 已冻结，而 $T_2$ 的优化目标是累乘值 $\hat{c}_1\hat{c}_2$ 的 ECE——所以不管 $T_1$ 标得好不好，$T_2$ 都会尽力让"两个乘起来"贴近经验值。这是它能把 ECE 从 0.0875 压到 0.0001 的原因；只标单个 $c_2$ 做不到。

### 5.3 这套方法的两个局限

1. **一个位置只有一个标量温度，只能修系统性偏差。** 如果可靠性图形状是"两头准、中间偏"这种非单调畸变，一个温度修不了。论文图 6 校准后 ECE 降到约 1%、不是 0，剩下的那 1% 大概就是这类修不掉的部分。
2. **逐位置贪心不保证全局最优。** 理论上存在"$T_1$ 稍差、$T_2$ 就能好很多"的组合被顺序结构排除掉了。**这是拿最优性换可行性。**

这两条原文没有明说，是从方法本身推出来的。

### 5.4 悬置的一点

论文说去掉早停是因为锯齿状 SPS 悬崖会让调度器卡在局部最优，但反复构造仍得不到"锯齿让早停错过全局最优"的例子，除非曲线出现幅度足够大的反弹。这只能说明两种可能：要么真实硬件的 SPS 波动比玩具模型剧烈得多，要么还有别的原因。原文没给数据，此处存疑；等有真实硬件时，第一件事就是 profile 一条真实 SPS 曲线、看它相邻比值波动多大。

### 5.5 两种 hidden state communication 不要混起来

DSpark 里有两处跟"传隐状态"有关，很容易混成一件事，但它们发生在不同阶段、用的是不同优化手段。分清楚之后，第 1.2 节的接口族分类也就有了着落。

**第一处是推理阶段、结构性的。** 第 1.2 节已经说过，DSpark 的并行 backbone 建在 DFlash 上，草稿器要把 target 若干层的隐状态投影进来、注入每一层的 key 和 value。这是**特征级接口的固有成本**：草稿器每起草一步都要读 target 的内部表示，这个需求省不掉。在单机内它走的是显存带宽，草稿器与 target 不共置时才会变成网络带宽。

**第二处是训练阶段、工程性的。** 训练 draft 模型需要 target 的输出分布当监督信号（式 8 的 $c_k^*$、式 10 的 $\mathcal{L}_{tv}$ 都要用）。分布式训练时 target 和 draft 跑在**不同 worker** 上，所以监督信号必须跨 worker 传。朴素做法是直接传分布，那是词表大小 $\mathcal{V}\approx 10^5$ 量级的向量，原文原话是 "creates a significant bandwidth bottleneck"；优化做法是**只传 LM head 之前的隐状态** $h \in \mathbb{R}^{d}$——因为 logits 就是 $W_{\text{LM head}} \cdot h$，而 draft 模型共享 target 的 LM head（且冻结），拿到 $h$ 就能在本地还原分布。通信量因此从每 token $\mathcal{V}$ 降到 $d$，差一个多数量级。

两处放在一起看，能看到同一个取向：**同一个 $h \in \mathbb{R}^{d}$，在卡内是显存带宽问题，跨设备就是网络带宽问题。** 训练侧那处是主动把 $\mathcal{V}$ 压到 $d$，推理侧那处则是这个接口族天生就要付的账。
