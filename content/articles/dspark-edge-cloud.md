# DSpark 端云迁移：这条路走不通

我做端云推理，读这篇论文的时候一直在琢磨一件事：能不能把 DSpark 迁到端云协同里——草稿器放端侧，target 放云上。最初的设想是保留置信度头和硬件感知调度器，把调度器的容量曲线从"batch 大小 → 引擎每秒步数"换成网络侧的"传输量 → 有效传输能力"。这个设想现在可以下结论了：走不通。

**断点在草稿器的输入上。** DSpark 的并行 backbone 建在 DFlash 上，这类草稿器要吃 target 的隐状态——起草时注入 target 若干层的隐状态，训练时也是这么训的。在数据中心里这不是问题：draft 和 target 共置，隐状态走显存带宽，不出卡。一旦拆到端云两侧，账就变了：target 在云上验证完，新接受 token 的隐状态要传回端侧给草稿器用；下一轮草稿传上去验证，验证完更新过的隐状态再传回来。**整个 draft–target 循环里，target 的隐状态要反复跨链路传。**

而且每轮传回来的不是几个 token id，是接受位置上的 $d$ 维隐状态，体积比 token 大得多。就算把多层特征融合挪到 target 一侧做完、只传融合后的数据（这是免费的优化，shape 还能更小），压的也只是 payload。**真正要命的是往返次数**：每一轮"送草稿上去—等验证—带隐状态回来"都是一次串行往返，下一轮起草必须等这一轮的隐状态到手才能开始。RTT 就这样压在关键路径上，成为瓶颈、成为每轮时延的硬性下界——压缩、错峰、加大 batch 都摊不掉它，只有减少往返次数才动得了。

**我试过绕。** 既然瓶颈是反复传隐状态，那让草稿器根本不吃 target 特征行不行：把 draft 和 target 纯拆开，draft 在端侧自己做 prefill、直接处理 prompt 再预测。我改了 vLLM 试了一版（做得比较粗）——接受率暴跌，很不稳定。原因也简单：这类草稿器训练时就是吃着 target 的隐状态学的，把特征抽掉，等于喂它从没见过的输入。

**就算接受草稿质量暴跌，想保留的部分也保不住。** 我最初想留的是 DSpark 的硬件感知调度器。但调度器离不开置信度头——没有置信度头，"给数"的一环就没了，调度器无从谈起；而置信度头需要训练，训练就离不开 target，不传隐状态，置信度头也难以做出来。一环扣一环，最后"迁过去的 DSpark"里什么都不剩。想保留调度器做端云协同，这个想法业内其实早就否定过了，我算是自己又走了一遍才被说服。

**对之前判断的修正。** 我原来的读后感里写过：隐状态的流转发生在草稿模型内部，不涉及跨设备传递；论文里的 "hidden state communication" 只是训练侧的工程优化。这个判断对了一半——

"hidden state communication" 确实是"传隐状态"，但在**训练侧**，这半条我维持原判：

- 训练 draft 模型需要 target 的输出分布当监督信号（式 8 的 $c_k^*$、式 10 的 $\mathcal{L}_{tv}$ 都要用）
- 分布式训练时 target 和 draft 跑在**不同 worker** 上，所以监督信号要跨 worker 传
- 朴素做法是直接传分布，那是词表大小 $\mathcal{V}\approx 10^5$ 个数的向量，原文原话是 "creates a significant bandwidth bottleneck"
- 优化做法是**只传 LM head 之前的隐状态** $h \in \mathbb{R}^{d}$：因为 logits 就是 $W_{\text{LM head}} \cdot h$，而 draft 模型共享 target 的 LM head（且冻结），拿到 $h$ 就能在本地还原分布
- 通信量因此从每 token $\mathcal{V}$ 降到 $d$，一个多数量级

核实过：整篇论文里 "worker" 只出现 3 次，全部集中在训练小节（§5.1）；推理部分（§5.3/§5.4）没有任何跨设备通信的描述。论文的设定本来就是共置，它没考虑过端云要付的账。

错的是另一半。"隐状态不出卡"只在 draft 与 target 共置时成立；拆到端云，隐状态每轮都要过链路，而且要反复传。我当时没意识到草稿器要吃 target 的特征，把"传隐状态导致时延增加"这个顾虑轻易放下了——现在看，这个顾虑不但成立，而且是致命的。

顺带一句：论文还说吞吐和单用户时延这对目标在它的场景里"解耦"了，理由是并发被每请求固定的 KV-cache 容量和可用流量池限制住，有效批大小长期远低于算力饱和点。这个前提对端云也不成立——端云的约束是往返轮次的串行依赖和上行带宽。不过这一点已经不重要了：架构本身就迁不过去。

所以结论很短：**DSpark 的置信度调度这套东西很好，但它的设计前提——草稿器随时能读到 target 的隐状态——在端云场景里不成立。** RTT 卡在关键路径上，这套架构迁不过去。端云协同推理要找不依赖 target 特征的架构，那是另一个话题了。
